# ADR · A bounded tutor harness with deterministic learning authority

**Status · Provisionally supported, pending product-architecture review, 2026-11-13.** Scope is one authenticated learner and one five-minute introduction session. This decision follows §§4–8 of the separately supplied `CODEX_ENGINEERING_SPEC_V1.md` and the Next.js/TypeScript baseline at `d712f12`. Candidate services and indicative pricing are Phase 0 planning inputs. No provider or avatar technology has been selected or provisioned. [Figma experience mapping](EXPERIENCE_TO_CODE_MAP.md)

## Decision

Use a modular Next.js/TypeScript monolith, one managed PostgreSQL database and one allowlisted identity. Keep a pure, versioned curriculum and learning policy in the repository. Use one session coordinator with Zod-validated commands and provider adapters. Phase 1 can run the same presentation contract with a scripted event driver. Phase 2 implements the authoritative deterministic session lifecycle. Phase 3 adds a live voice adapter and a small model-proposal boundary. Phase 4 may extend that boundary to one consented image activity. The monolith shares types and invariants across those stages without bringing in an agent framework, queue, vector store or multiple services.

| Authority | Sufficient for | Boundary |
| --- | --- | --- |
| Model instructions | Patient persona, brief French welcome and explanations, natural English reformulation in a supplied situation, acknowledging requests and helping the learner repair meaning. | Supply the current goal, approved context, current assistance and expected response. Treat wording, interpretation and assessment as fallible. Prompts cannot enforce consent, valid turns, retention, quotas or durable effects. |
| Deterministic client and server logic | Capture/permission controls, rendering, localization and a11y, playback/replay of approved audio, turn ownership guards, availability and timeout handling, permission checks, prerequisites, evidence policy, scheduling, budgets, idempotency and checkpoint commits. | Browser owns actual device and audio rendering. Server owns permissions, durable teaching state, evidence and spend controls. Browser-derived events describe observations and carry no authority to change mastery. |
| Bounded tutor harness | Coordinate asynchronous voice events, retrieve minimized capability context, validate a model-selected repair technique, dispatch approved prompts/overlays, discard late output, resume from a checkpoint and mediate later frame analysis. | A single orchestrator receives typed events, validates proposals and calls narrow handlers. The learning engine selects lawful progression. The model has no arbitrary search, records, curriculum editing, progress writes or unrestricted tools. |

A single scripted first encounter and user-clicked replay or French help need ordinary handlers. The first live integration needs orchestration where a model suggestion intersects a specific session/turn, cancellation, external transport or evidence. Implement `requestScaffold` first and feed accepted actions back to the model as structured results. Keep prompt selection, attempt recording, progression and finishing as internal deterministic functions initially. Expose a proposal for each only if a concrete test demonstrates a benefit. Standalone TTS and browser ASR can be fallback adapters, with distinct provider notices and evidence provenance. They cannot satisfy the live bilingual turn-taking gate.

The model can propose scoped teaching moves or provisional observations. Only deterministic application services can select curriculum progression or write authoritative learner memory, including checkpoints, accepted evidence, capability state and due reviews. The harness validates input and routes proposals to those services. A valid proposal alone grants no write or progression authority.

## State and event contracts

| State | Owner and lifetime | Invariant |
| --- | --- | --- |
| Media turn | One logical reducer per active media connection, on the client for immediate capture/playback status. `idle`, `connecting`, `tutor_speaking`, `listening_open`, `learner_speaking`, `processing`, `thinking_pause`, `interrupted`, `recovering`, `offline`, `ended`. Server keeps last checkpoint media summary and connection lease. | On reconnect start a fresh media epoch with mic off. Previous transport flags do not reopen devices. Render actual output/capture readiness. Audio callbacks cannot advance the lesson. |
| Pedagogical activity | Server controller with pure policy and pinned lesson version. `orientation`, `model`, `guided_attempt`, `independent_attempt`, `diagnostic_probe`, `scaffolded_retry`, `transfer_attempt`, `recap`, `review_due`. | Only an accepted command may advance the checkpoint. A device error or turn silence leaves teaching progress intact. |
| Overlay | Typed view state from controller directives plus local accessibility preferences and explicit learner actions. `english_caption`, `french_support`, `context_image`, `replay_controls`, `visual_choice`, `feedback`, `device_error`. | Each overlay carries trigger, reason, associated turn, dismiss/restore policy and accessible text. Cancel obsolete generated instructions. Access preferences remain available and relevant cue exposure is tracked per attempt. |

Normalize UI/provider events into a shared typed envelope with source, event ID, session ID, connection epoch, turn ID, optional output ID and time. Durable mutations also require content version, expected revision and idempotency key. Derive learner identity from the server session. Scope interruption to the old output and invalidate its pending proposals/captions before opening or continuing the learner’s turn. Use provider detection to suggest onset and endpoint, gate automatic tutor responses until the turn is confirmed, and offer a manual path. Thinking pauses produce no automatic error, confusion label, failed attempt or advance. Treat echo/noise and incomplete speech as unassessed until clarified. Make one gentle check-in configurable. Preserve immediate mute/end even when server confirmation is pending. [Realtime voice activity detection](https://developers.openai.com/api/docs/guides/realtime-vad)

| Spec contract | Initial disposition and guard |
| --- | --- |
| `requestScaffold` | Phase 3 model proposal for `repeat`, `slow`, `french`, `example` within an active repair-capable turn. Match capability, aid allowlist, and intervention limits. `image` resolves to a curated asset if approved. Explicit Aide bypasses the model and restores available support. |
| `presentPrompt` | Internal controller command keyed by approved prompt ID and variant. The model may speak approved wording or phrase a teaching explanation. A scored stimulus is pinned, including its source and exposed aids. |
| `recordAttempt` | Server builds provenance from accepted events. A future assessment proposal accepts bounded rubric categories and confidence, without raw utterances in durable payloads. Browser-relayed provider output starts provisional. Never accept caller-supplied correctness as authoritative. |
| `requestNextActivity` and `finishSession` | Internal progression and explicit learner end initially. The model may verbalize a recap from approved factual claims. The server determines review and saves the checkpoint. |
| `requestVisionFrame` | Phase 4 optional request to offer an activity-specific preview. Camera starts off and requires explicit permission to open. Actual upload requires separate explicit confirmation bound to the exact frame and purpose. Time/size/rate bounds, cancellation, server authorization and a no-camera equivalent are mandatory. Camera availability and consent do not determine general learning progression. |

Return compact errors such as `STALE_TURN`, `UNSUPPORTED_ACTION`, `CONSENT_REQUIRED` and `BUDGET_EXHAUSTED`. Drop stale results, display actionable French recovery for learner-visible failures and avoid automatic repeated tool calls. Authenticate and check ownership and consent before external operations. Protect each mutation with transaction/revision guards and a unique operation key, including end. Return the original result on a same-payload retry and reject mismatched key reuse. Deduplicate provider event IDs separately. For call startup, reserve one lease before the provider request, record call ID as soon as possible and reconcile failed or ambiguous creation within a bounded window before retry. A database transaction cannot make an external media call atomic.

## Learner memory, assessment and recovery

- Keep `capability` definitions, prerequisites, prompt variants, rubric and content versions in source-controlled data. Persist references alongside `learner`, `session`, `attempt`, `evidence`, `capability_state`, `consent` and `session_event`. For this slice, use SQL migrations and one adapter with bounded, typed queries. Use a transaction to advance the session revision and append an accepted attempt/evidence/event and review state. Keep ephemeral media and raw transcript outside the durable store.
- A checkpoint contains phase, active capability, current approved variant, last committed turn, support context, revision and resume status. Reconnect reads that checkpoint and gets a new connection epoch. Confirm committed versus pending before asking for repetition. An unsent utterance can be lost without raw recording. Explain this plainly, replay the prompt on request and offer typing. Never replay unacknowledged audio or silently enable mic/camera. Offline practice may be generic and clearly unsaved. Private responses and media stay out of the service worker and HTTP caches.
- Store stimulus and response modalities separately, variant/speaker, first or repeated exposure, speed/replay, captions/French/model/visual cues actually shown, learner corrections, assessment source and rubric version, confidence, phase, time and outcome. Distinguish supported success, independent performance on the measured dimension, unsure, skipped and technical failure. A bare name can satisfy the communication goal. A transcript alone cannot establish that speech was intelligible. If a caption reveals the question, a successful spoken response can still provide production evidence with an assisted stimulus. A model assessment remains provisional until calibrated on consented, reviewed examples.
- English and French instructional overlays are visible from the beginning. The deterministic policy fades an individual aid for the relevant capability only after demonstrated independence. In Phase 4 use repeated evidence across contexts, including transfer and later retrieval, before advancing skill status or fading support. One early success can justify a fresh optional probe. Always allow immediate aid restoration and honor accessibility preferences. Use simple, inspectable `new`/`developing`/`emerging`/`proficient`/`needs_review` rules and version them. Start with a review candidate after roughly 2–3 days, configurable and subject to pedagogical review. Recap claims follow the same evidence constraints.
- Preserve the `everyday-english-v1` JSON validator and five original activity IDs. A different private origin cannot read Pages storage. Prefer explicit export on the old origin and authenticated preview/import of valid v1/v2 records. Classify as legacy practice with uncertain modality/assistance and provenance. Keep original activity IDs/content version, bound file size and deduplicate imports. Never replace existing session/evidence on bad or unsupported files. The original remains intact unless the learner deletes it separately. The pilot can begin with a fresh record if migration is declined, with the compatibility choice documented. ## Alternatives and review gates

Prompt-only is suitable for short dialogue wording and quick experimentation. It leaves recovery, evidence and permissions undefined. A deterministic-only session is sufficient for the shell, learning policy and offline fallback. It cannot handle natural bilingual response and repair well by itself. A general agent would add broad permissions, cost and state opacity. The bounded harness requires explicit schemas and fixtures and confines provider complexity to an adapter. Approve the authority split now. Select hosting, identity and database before Phase 2, authorize voice processor and caps before Phase 3, and review evidence thresholds, portrait/animation/video and image processing independently.
